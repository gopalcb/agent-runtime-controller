Point to the change you mean

“Make the header smaller” sounds clear until someone has to decide which header, how small, and at what screen size. Runtime Controller keeps that visual context beside the written request.

A developer can draw a rectangle on a blank canvas to describe something new. For an existing app, they can open a local URL, highlight an element and describe the change. Each instruction becomes a saved work item rather than disappearing into a long chat.

For example, a request might be: “Reduce this header's height, centre the menu, and keep the project title on the left.” The captured rectangle and viewport explain the intended area. An element selection can also include its selector, styles and sanitized HTML or text. These are clues for finding the source, not a guarantee that a DOM element maps directly to one component.

One request, four stages

  1. CaptureSave a description with a rectangle or an element reference.
  2. SelectChoose the pending items and confirm the scope of the run.
  3. ImplementThe backend gives Codex the saved instructions and project directory.
  4. ReviewRead the output, inspect the changes and check the application.

The Angular interface talks to a NestJS API running on the same machine. The API selects the project session, which owns its work-item store, capture browsers, installer and Codex connection. The coding agent works on the selected project's files.

A completed turn is a review point. It means Codex finished its turn, not that the resulting code has independently passed acceptance testing. The developer still reviews the diff and the reported checks.

Inside the implementation

The application uses familiar web technologies. The part that connects them is a small TypeScript runtime that translates saved work into an agent turn and translates protocol notices back into run state.

1. The UI submits IDs, not a second copy of the work

After confirmation, the frontend sends the selected instruction IDs and any extra context to POST /api/execute. The backend reads the saved records, so it can validate that every requested item still exists and is pending.

Source excerpt: frontend/src/app.ts, inside execute().

const run = await this.mutate('/execute', { instructionIds: this.selectedItems().map(item => item.id), prompt: this.prompt.trim() }) as Run;

The shared mutate() helper adds the current X-Project-Id and X-Builder-Token headers. The API rejects stale project requests. The execution route also checks that installation has completed before handing the request to the runtime.

2. TypeScript freezes the run's inputs

Runtime.execute() rejects duplicate or unknown IDs and prevents a second active run. It copies the selected instructions and settings into a run record, marks those items as running, then starts asynchronous dispatch. The API can return the run ID while the agent continues working.

The runtime starts a Codex thread with the project directory as cwd, the selected sandbox and approval settings, and developer instructions to follow project conventions. It then builds the actual task from the saved snapshot.

Source excerpt: backend/runtime.ts, after the thread has started. requestSettings supplies the working directory, approval policy and optional model.

const prompt = [
        'Implement these saved visual instructions in this project.',
        `Project: ${this.store.root}`,
        `Additional user context: ${run.prompt}`,
        'Visual instructions (CSS pixels with viewport reference):',
        JSON.stringify(run.instructions, null, 2),
      ].join('\n');
      const result = await transport.request('turn/start', {
        ...requestSettings,
        threadId: run.threadId,
        input: [{ type: 'text', text: prompt }],
        sandboxPolicy: sandboxPolicy(settings, this.store.root),
        ...(settings.reasoningEffort ? { effort: settings.reasoningEffort } : {}),
      });

This is where the work items become an agent request. Their JSON includes the descriptions and visual reference data. The runtime asks Codex to interpret that context and edit the source; it does not convert rectangle coordinates into generated CSS by itself.

3. The adapter talks to a local process

CodexTransport launches codex app-server --listen stdio:// using Node's spawn(). It completes initialization, checks the effective configuration and disables inherited integrations for its owned execution. Each request receives an ID so the response can resolve the correct pending promise.

Source excerpt: backend/codex.ts. Each JSON-RPC message occupies one line.

private send(message: any) {
    if (!this.child || this.child.stdin.destroyed) throw new Error('Codex is not connected');
    this.child.stdin.write(JSON.stringify(message) + '\n');
  }

Node's readline reads the process output. Responses resolve requests; notifications update run state; supported command or file-change approval requests are routed back to the UI. A timeout is reported rather than automatically retrying work that might already have started.

4. Progress returns through persisted state

The backend handles notices such as item/completed, turn/completed and thread/tokenUsage/updated. It records completed agent messages, run status and the greatest cumulative token report for the thread. Missing usage remains unreported.

Angular polls the local state API every two seconds. This implementation does not use a browser WebSocket or a token-by-token stream. The active run shows output in the runtime page; finished runs remain in history. Cancelling a run stops owned execution, but cannot undo edits the agent already made.

A package that stays with the project

The repository is named agent-runtime-controller. Its npm package currently retains the name @gb-systems/visual-agent-builder, and exposes the runtime-controller command. Installation uses a locally built archive.

From the controller checkout, install dependencies and build the package:

npm ci
npm --prefix frontend ci
npm pack

Then install the generated archive as a development dependency in the application you want to work on. The README includes the required dependency override and a copyable agent prompt. The npm lifecycle invokes Python, starts or finds the controller, and opens the installation page. That page shows real step status while the installer checks prerequisites and deploys the runtime files.

There are two kinds of installed files: the application itself under node_modules, and project guidance and records under .codex. The installer also exposes packaged skills through .agents/skills.

File hashes let the installer distinguish its own unchanged files from local edits. Reinstallation updates files it still owns and preserves conflicts for review. Reset removes unchanged managed runtime files while keeping work history, settings and project memory.

The generated .codex/runtime-controller/codex.py launcher can ensure the controller is running before starting Codex. It is an explicit entry point: opening an IDE or running the ordinary Codex command does not automatically invoke it.

Why the boundaries matter

Project context is part of every operation. Switching folders changes the active store and closes the old capture browsers. The controller blocks switching during an installation or active run, and rejects requests from stale tabs.

Visual capture uses an owned browser. It does not borrow a personal browser's logged-in session. Existing-page capture is limited to local URLs and same-origin navigation; closed shadow roots and cross-origin frames cannot be selected.

Guidance and credentials have different homes. Portable instructions and explicit memory notes belong to the project. Native Codex authentication, private session history and generated memory are not copied into the template.

Local execution still needs review. The default sandbox is workspace-write, with command network access disabled. Settings can grant broader permissions. The tool is designed for a trusted local developer, not as a hosted service for multiple users.

What has been checked

The repository includes API and runtime tests, installer tests, packaged-install checks and browser tests using temporary projects. Agent transports are simulated where needed so verification does not launch real coding work against a user's project. These checks exercise controller behavior; they do not establish the quality of every change a model may produce.
